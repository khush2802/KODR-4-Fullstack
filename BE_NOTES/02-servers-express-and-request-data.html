Servers, Express
and Getting Data In

A server is a machine that is programmed to serve its users. This note takes that sentence apart — what the machine is, what "serve" means, and the four different doors a client can push data through.

HTTP Express Routing params · query · body
01
What Is a Server?
Start with the sentence, then take it apart
Working Definition

A server is a machine that is programmed to serve its users — and the users we are talking about are called clients.

That definition is correct, and it is where most people stop. Take it one layer deeper, because the word "machine" is doing something sneaky in that sentence.

The machine is not special

There is no such thing as "server hardware" you must buy. The laptop in front of you becomes a server the moment you run a program that waits for requests. Server is a role, not a device.

And the role flips depending on who is asking. Your Express app is a server when React calls it. That very same app is a client when it calls MongoDB. When we get to microservices, every service is both at once.

React app  ──request──▶  Express app  ──request──▶  MongoDB
  client                 server + client              server

"Programmed to serve" means one loop

Strip away every framework and a server is one idea: a program that starts, claims a door number, and then waits forever. A request arrives, it responds, it goes back to waiting. Nothing more.

Start the program
node index.js — your code is now a running process.
Bind to a port
Ask the operating system: send me anything that arrives on 3000.
Wait
The process does not exit. It sits idle, costing almost nothing.
Request arrives → run a function → send a response → wait again
Everything you will build this month is a variation on this line.
02
Ports and the Listening Loop
Two questions almost nobody can answer properly

Question 1 — what is a port, really?

Your machine has one IP address but runs many programs that want network traffic. When a packet arrives, the operating system needs to know which process gets it. The port number is that routing label. IP finds the machine; the port finds the program.

Analogy

The IP address is the building's street address. The port is the flat number. The postman gets to the right building with one and to the right door with the other. Only one family can live in flat 3000.

Verify — run this in class

Start your server on port 3000. Now open a second terminal and start another one on 3000 too.

Terminal 
node index.js
# Error: listen EADDRINUSE: address already in use :::3000

EADDRINUSE is the OS telling you flat 3000 is occupied. This is the single most common error in backend development, and now you know it has nothing to do with your code.

PortUsuallyNote
80HTTPThe default when a browser sees http:// with no port.
443HTTPSThe default for https://. This is why you never type a port on real websites.
3000 / 5000 / 8080DevelopmentConvention only. Nothing special about them.
27017MongoDBYour database is a server too, listening on its own port.

Question 2 — why doesn't the program exit?

Run a normal script and Node finishes the last line and quits. Run app.listen(3000) and the process sits there forever, even though there is no more code. Ask yourself why before reading on.

Key Concept

Node exits when it has nothing left to do. A listening server registers an active handle with the event loop — an open socket that might produce work at any moment. As long as one active handle exists, the event loop has a reason to keep spinning, so the process stays alive. Ctrl + C is you telling the OS to kill it.

You see EADDRINUSE when starting your server. What actually happened?

03
What a Request Actually Looks Like
There is no magic here — it is a string

Before Express hands you a neat req object, something arrives over the network. See it with your own eyes. Start any server on 3000 and run this:

Terminal 
curl -v "http://localhost:3000/notes/5?sort=desc"

The lines starting with > are what your machine sent. It is plain text:

Raw HTTP request 
GET /notes/5?sort=desc HTTP/1.1
Host: localhost:3000
User-Agent: curl/8.4.0
Accept: */*
(blank line)
(body would go here, if there were one)
PartExampleWhat it carries
MethodGETWhat you want done. Verb.
Path/notes/5Which thing you want it done to. Noun.
Query string?sort=descOptions and filters. Everything after the ?.
HeadersHost, AcceptMetadata about the request. Key–value pairs.
Blank line\r\nThe separator that says "headers are finished".
BodyJSON, form dataThe payload. Everything after the blank line.
💡

The Host header exists because one server IP can host hundreds of websites. Without it, a machine receiving a request for / would have no idea which site you meant.

Hold on to this picture. In section 6 you will see that req.params, req.query and req.body are not three magical objects — they are three different slices of the text above.

04
Your First Express Server
Six lines, and you know what every one of them does
Step 1 — Install
Terminal 
npm init -y
npm install express
Step 2 — Write it
index.js 
import express from "express";

const app = express();

app.get("/", (req, res) => {
  res.send("Server is alive");
});

app.listen(3000, () => {
  console.log("Listening on http://localhost:3000");
});
LineWhat it isWhat it does
express()appCreates the application — really just a request handler with a route table attached.
app.get()routeAdds an entry to that table: "if the method is GET and the path is /, run this function".
reqrequestEverything the client sent you.
resresponseYour tools for replying. Nothing is sent until you call a method on it.
app.listen()3000Binds the port and starts the waiting loop.

What is Express, actually?

Node already ships an http module that can do all of this. Express is a thin layer on top that gives you two things: a router so you stop writing giant if-else chains on req.url, and a middleware chain so you can run shared logic before your handlers.

Key Concept

req and res are not Express objects. They are Node's own IncomingMessage and ServerResponse, with extra convenience methods bolted on. Prove it: req instanceof http.IncomingMessage returns true. Express borrowed them; it did not invent them.

💡

Run your server with node --watch index.js and it restarts on every save. You do not need nodemon for this any more — it is built into modern Node.

05
Routes
A route is method + path + handler. That's the whole idea.
index.js 
app.get("/notes",     (req, res) => res.send("list of notes"));
app.post("/notes",    (req, res) => res.send("created a note"));
app.put("/notes/1",  (req, res) => res.send("replaced note 1"));
app.delete("/notes/1",(req, res) => res.send("deleted note 1"));

Notice that /notes appears twice with two different methods and two different handlers. The path alone does not identify a route — the method is half of the address. That idea becomes the foundation of REST in the next note.

⚠️

Routes are an ordered list, and the first match wins. Express walks your routes top to bottom. This causes a bug you will hit today.

The route-ordering trap

Broken 
app.get("/notes/:id",     handlerA);
app.get("/notes/search",  handlerB);   // never runs!

// GET /notes/search matches the FIRST line,
// with req.params.id === "search"
Fixed 
app.get("/notes/search",  handlerB);   // specific first
app.get("/notes/:id",     handlerA);   // dynamic last
Rule to remember

Specific routes go above dynamic routes. A :param will happily swallow any word you put in that position, including words you meant as fixed paths.

Sending responses

MethodSendsUse for
res.send()Guesses the content typeQuick tests only
res.json()JSON + correct Content-Type headerEvery API response
res.status(404).json()JSON with a chosen status codeAnything that is not a plain success
res.sendStatus(204)Status code with no bodySuccessful deletes

You defined /notes/:id before /notes/archive. A request to /notes/archive arrives. What happens?

06
The Four Channels
Every byte a client sends you arrives through one of these

Go back to the raw request from section 3 and label it. That is all Express is doing for you:

POST /notes/5?sort=desc HTTP/1.1
          ↑ req.params   ↑ req.query
Authorization: Bearer abc123   ← req.headers
Content-Type: application/json

{ "title": "Backend Day 1" }   ← req.body
ChannelLives inUse it for
req.paramsInside the pathWhich resource — an id or a slug
req.queryAfter the ? in the URLHow to filter, sort, paginate
req.bodyAfter the blank lineThe data being created or updated
req.headersKey–value lines at the topAuth tokens, content type, metadata
⚠️

Never put a password or token in the query string. URLs are written into server access logs, browser history, and the Referer header sent to third-party sites. Secrets belong in the Authorization header or the body — never the URL.

07
Route Params
Naming which specific thing you want
index.js 
app.get("/notes/:id", (req, res) => {
  console.log(req.params);        // { id: '5' }
  res.json({ requested: req.params.id });
});

// Multiple params are fine:
app.get("/users/:userId/notes/:noteId", (req, res) => {
  console.log(req.params);        // { userId: '2', noteId: '9' }
});
⚠️

Params are always strings. /notes/5 gives you "5", not 5. So note.id === req.params.id is false when your ids are numbers, and it fails silently — no error, just an empty result and a confused student.

The fix 
const id = Number(req.params.id);
const note = notes.find(n => n.id === id);

if (!note) {
  return res.status(404).json({ error: "Note not found" });
}
💡

Note the return. Without it, execution continues and you try to send a second response, which produces Cannot set headers after they are sent to the client — another error you will meet today.

08
Query Strings
Optional instructions about how you want the data
GET /notes?search=react&limit=10&sort=desc 
app.get("/notes", (req, res) => {
  console.log(req.query);
  // { search: 'react', limit: '10', sort: 'desc' }

  const limit = Number(req.query.limit) || 20;
  res.json(notes.slice(0, limit));
});
Design Rule

Params identify. Query modifies. /notes/5 says which note. ?sort=desc&page=2 says how you want the list presented. If you find yourself writing /notes?id=5, that id belongs in the path instead.

⚠️

Query values are strings too. ?limit=10 gives "10", so req.query.limit + 1 is "101". And ?active=false gives the string "false", which is truthy. Both bugs are extremely common.

A client sends GET /notes?active=false and your code does if (req.query.active) { ... }. Does the block run?

09
The Request Body
And the one line of setup everybody forgets
Caution — try this the broken way first
Broken 
app.post("/notes", (req, res) => {
  console.log(req.body);   // undefined 😱
  res.json(req.body);
});

Send a POST with a JSON body and req.body is undefined. The data definitely arrived — so where did it go?

Key Concept

The body does not arrive as an object. It arrives as a stream of raw bytes, in chunks, after the blank line. Something has to collect those chunks, look at the Content-Type header to learn the format, and parse them. Express does not do that by default — parsing every body on every request would be wasteful. You have to opt in.

Fixed 
const app = express();

app.use(express.json());                     // parses JSON bodies
app.use(express.urlencoded({ extended: true })); // parses HTML form bodies

app.post("/notes", (req, res) => {
  console.log(req.body);   // { title: 'Backend Day 1' } ✅
  res.status(201).json(req.body);
});

That app.use(...) line is your first piece of middleware — a function that runs on every request before your route handlers. We will pull middleware apart properly in its own session, including writing our own version of Express's chain.

Verify
Terminal 
curl -X POST http://localhost:3000/notes \
  -H "Content-Type: application/json" \
  -d '{"title":"Backend Day 1"}'
💡

Drop the -H "Content-Type: application/json" and watch req.body become empty again. The header is how the parser knows the bytes are JSON. Sending data is not enough — you must say what kind of data it is.

Try It Yourself
Build it before the next note — the Notes app depends on all of this
Base
  • Start a server on port 3000 that responds to GET /.
  • Add GET /profile/:username and return the username as JSON.
  • Add GET /search and echo back req.query.
Push
  • Add POST /echo that returns whatever body it receives. Make it work with curl.
  • Deliberately break the ordering: put /profile/:username above /profile/me and observe what happens. Then fix it.
  • Return a proper 404 with a JSON error when a resource does not exist.
Break
  • Read the port from process.env.PORT with a fallback to 3000, and start it on 4000 without editing the file.
  • Log every incoming request's method, path and timestamp — using app.use(), before your routes.
  • Run curl -v against your own server and map every part of the output back to the table in section 3.
One-Line Summary

A server is a program that claims a port and waits. A route is method + path + handler. And every byte a client sends reaches you through params, query, body or headers — four slices of one plain-text request.
