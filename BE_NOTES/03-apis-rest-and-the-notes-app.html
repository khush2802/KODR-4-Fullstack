APIs, REST
and the Notes App

Most courses teach REST as four HTTP methods. That is the syntax, not the idea. This note starts with the mess that existed before REST, so the rules land as obvious rather than arbitrary.

REST Resources Idempotency Status codes
01
What Is an API?
The word means interface, and that is the whole answer

API stands for Application Programming Interface. Skip the expansion and look at the middle word that matters: interface. An interface is an agreed way for two things to talk without either one knowing how the other works inside.

You already use dozens of APIs. Math.random() is an API — you call it, you get a number, and you have no idea what algorithm is inside. A TV remote is an API for a television. You press a button; you do not need to understand the circuit board.

Key Concept

An API is a boundary that lets one side change without breaking the other. That is the entire reason it exists. A Web API is that same contract, exposed over HTTP, so the two sides can be on different machines written in different languages.

Why doesn't React just talk to MongoDB?

Ask the room this before answering. There are three real reasons:

ConcernDirect DB access from the browserThrough an API
Security Database credentials ship to every user's browser Credentials stay on the server
Trust Anyone can run any query, including DELETE The server decides what is allowed
Change Rename a column and every client breaks Change the schema, keep the contract

That third row is the one people underrate. Your web app, your mobile app and your admin dashboard all speak to the same API. The API is the promise you keep while everything behind it is free to move.

02
The World Before REST
Understand the mess and the rules explain themselves

Early web APIs had no shared convention. Every team invented its own URLs. Real endpoints looked like this, in the same codebase:

Actual endpoints from the pre-REST era 
GET  /getUser?id=5
GET  /fetchAllUsers
GET  /user_list_v2
POST /createNewUser
POST /updateUserDetails
POST /deleteUserNow
POST /removeUserPermanent

Nothing here is technically wrong. It works. But every single endpoint has to be memorised, no two APIs look alike, and you cannot guess anything. Onboarding to a new API meant reading a 40-page PDF.

Now look closely at GET /getUser and notice the redundancy: the word "get" is in there twice. HTTP already had a verb. Everyone was ignoring it and inventing their own.

💡

In 2000, Roy Fielding — one of the authors of the HTTP spec itself — described a set of constraints for web systems in his doctoral dissertation and called it REST: Representational State Transfer. It is not a technology, a library, or something you install. It is a set of agreements.

03
The REST Idea
One sentence you should be able to recite
The Whole Thing

The URL names a resource — a noun. The HTTP method describes the action — a verb. Stop putting verbs in URLs, because HTTP already gave you a full set of them.

IntentPre-RESTREST
List all notesGET /getAllNotesGET /notes
Get note 5GET /getNoteById?id=5GET /notes/5
Create a notePOST /createNotePOST /notes
Replace note 5POST /updateNote?id=5PUT /notes/5
Delete note 5POST /deleteNoteNow?id=5DELETE /notes/5

Look at the right column. There are only two URLs — /notes and /notes/:id — doing the work of five. And once you know the pattern, you can guess a REST API you have never seen. GET /products/12/reviews needs no documentation.

Naming rules that follow from this

RuleBadGood
Nouns, not verbs/createNotePOST /notes
Plural collections/note/5/notes/5
Nesting for ownership/getNotesOfUser?u=2/users/2/notes
Lowercase with hyphens/blogPosts/blog-posts
Filters in the query/notes/search/react/notes?search=react

04
The Rules That Actually Matter
Four constraints, each with a consequence you will feel later
Rule 1 — Statelessness

Every request must carry everything needed to serve it. The server remembers nothing about you between requests. If you are logged in, you prove it again on every single call by sending your token.

Ask why before giving the answer. It sounds wasteful — until you draw this:

Request 1 ──▶ Load Balancer ──▶ Server A ✅
Request 2 ──▶ Load Balancer ──▶ Server B ✅
Request 3 ──▶ Load Balancer ──▶ Server C ✅

Any server can answer any request, because none of them remember you.
Remember This One

Statelessness is why you can scale. If server A held your session in memory, every one of your requests would have to come back to server A — and when A dies, you are logged out. When we run this app across multiple pods in Kubernetes, this constraint is what makes it possible.

Rule 2 — Uniform interface

Same resource naming, same methods, same status codes, everywhere. This is what lets a developer who has never seen your API guess how it works. Consistency is the feature.

Rule 3 — Client–server separation

The client owns the interface, the server owns the data. Either side can be rewritten completely as long as the contract holds. Your React app could be replaced by a Flutter app tomorrow and the API would not care.

Rule 4 — Cacheable

Responses can say whether they may be stored and reused. A CDN can cache GET /notes because it only reads. It can never cache a POST, because a POST changes something. This is why the read/write split in your methods is not a cosmetic choice.

⚠️

Be honest about this: REST is a convention, not a law, and almost no real-world API is fully RESTful. GraphQL, gRPC and tRPC exist because REST has genuine weaknesses — over-fetching, many round trips, no typed contract. Knowing REST's limits is what separates a developer from someone who memorised a tutorial.

05
Methods, Safety and Idempotency
Two words that sound academic and turn out to be about money
MethodDoesSafe?
GETRead a resourceSafe + idempotent
POSTCreate a new resourceNeither
PUTReplace a resource entirelyIdempotent
PATCHUpdate part of a resourceUsually not
DELETERemove a resourceIdempotent
Two Definitions

Safe means it changes nothing on the server — reading is safe. Idempotent means doing it five times leaves the system in the same state as doing it once.

Why this is not academic

A user clicks "Pay" and the network hiccups. Your client retries. Was the payment made once or twice?

POST /payments  ×3  →  three charges. Your customer is angry.
PUT /notes/5  ×3  →  note 5 has the same content. Nothing to fix.
DELETE /notes/5  ×3  →  note 5 is gone. Still gone. Still gone.

This is also why your browser shows "Confirm form resubmission" when you refresh after submitting a form. The browser knows a POST is not safe to repeat on its own. When we reach the payment gateway module, this exact problem is what idempotency keys exist to solve.

PUT vs PATCH

The note before 
{ "id": 5, "title": "Day 1", "body": "Express basics" }

// PUT /notes/5  with  { "title": "Day 2" }
// → replaces the whole thing. "body" is now gone.

// PATCH /notes/5  with  { "title": "Day 2" }
// → only title changes. "body" survives.

A flaky network causes the same request to be sent three times. Which method is the dangerous one?

06
Status Codes
Learn the five families, not the sixty numbers
2xx — You asked, I did it.
3xx — It lives somewhere else now.
4xx — You made a mistake.
5xx — I made a mistake.
CodeNameSend it when
200OKA successful read or update.
201CreatedA POST created something. Return the new resource.
204No ContentSuccess, but there is nothing to send back. Perfect for DELETE.
400Bad RequestThe client sent something malformed or missing.
401UnauthorizedI do not know who you are. Log in.
403ForbiddenI know exactly who you are, and you are not allowed.
404Not FoundThat resource does not exist.
409ConflictDuplicate email, version clash, that kind of thing.
500Server ErrorYour code threw. Never blame the client for this.
💡

401 vs 403 is asked in interviews constantly and most people get it backwards. 401 = who are you? 403 = I know who you are, and no.

⚠️

Returning 200 OK with { "error": "not found" } in the body is the most common REST mistake in student projects. The client checks the status code first. Lying in the status line breaks every tool that consumes your API — including the browser's own cache.

07
Building the Notes API
Two URLs, five routes, no database

We store notes in a plain array. No MongoDB today — a database would add a second new thing to learn and hide the REST lesson. Restart the server and your data is gone, and that is fine.

Design the contract before writing code

MethodPathDoes
GET/notesList all notes → 200
GET/notes/:idOne note → 200, or 404
POST/notesCreate → 201, or 400
PUT/notes/:idReplace → 200, or 404
DELETE/notes/:idRemove → 204, or 404
Habit worth building

Professionals write this table before the code. It is the contract. Once it is agreed, the frontend team can start building against it while the backend is still empty.

Step 1 — Setup
Terminal 
mkdir notes-api && cd notes-api
npm init -y
npm install express
# then add  "type": "module"  to package.json
Step 2 — The whole API
index.js 
import express from "express";

const app = express();
app.use(express.json());

let notes  = [{ id: 1, title: "Day 1", body: "Express basics" }];
let nextId = 2;

// ── READ ALL ──────────────────────────────
app.get("/notes", (req, res) => {
  const { search } = req.query;

  const result = search
    ? notes.filter(n => n.title.toLowerCase().includes(search.toLowerCase()))
    : notes;

  res.status(200).json(result);
});

// ── READ ONE ──────────────────────────────
app.get("/notes/:id", (req, res) => {
  const note = notes.find(n => n.id === Number(req.params.id));

  if (!note) {
    return res.status(404).json({ error: "Note not found" });
  }

  res.status(200).json(note);
});

// ── CREATE ────────────────────────────────
app.post("/notes", (req, res) => {
  const { title, body } = req.body;

  if (!title) {
    return res.status(400).json({ error: "title is required" });
  }

  const note = { id: nextId++, title, body: body ?? "" };
  notes.push(note);

  res.status(201).json(note);
});

// ── REPLACE ───────────────────────────────
app.put("/notes/:id", (req, res) => {
  const id    = Number(req.params.id);
  const index = notes.findIndex(n => n.id === id);

  if (index === -1) {
    return res.status(404).json({ error: "Note not found" });
  }

  const { title, body } = req.body;

  if (!title) {
    return res.status(400).json({ error: "title is required" });
  }

  notes[index] = { id, title, body: body ?? "" };
  res.status(200).json(notes[index]);
});

// ── DELETE ────────────────────────────────
app.delete("/notes/:id", (req, res) => {
  const id    = Number(req.params.id);
  const index = notes.findIndex(n => n.id === id);

  if (index === -1) {
    return res.status(404).json({ error: "Note not found" });
  }

  notes.splice(index, 1);
  res.sendStatus(204);
});

app.listen(3000, () => console.log("http://localhost:3000"));

Five details worth pausing on

DetailIn the codeWhy
Number()req.params.idParams are strings. Without this, === never matches numeric ids.
returnbefore every resStops execution. Without it you send two responses and Express throws.
201on POSTSays "I made something new", and returns it so the client learns its id.
204on DELETESuccess with no body. Do not invent a fake success object.
400missing titleNever trust the client. Validate before you store.
⚠️

Add a GET /notes/search route to this file and put it above /notes/:id, or it will never run — the dynamic route matches first. This is the ordering trap from Note 02, and it will find you.

08
Testing It
The browser can only do GET — you need better tools

Typing a URL into Chrome always sends a GET. To test POST, PUT and DELETE you need curl, Postman, or the REST Client extension in VS Code. Learn curl — it works everywhere, including on a server over SSH.

Terminal 
# List all
curl http://localhost:3000/notes

# One note
curl http://localhost:3000/notes/1

# Create — watch for 201 in the response headers
curl -i -X POST http://localhost:3000/notes \
  -H "Content-Type: application/json" \
  -d '{"title":"Day 2","body":"REST"}'

# Replace
curl -X PUT http://localhost:3000/notes/1 \
  -H "Content-Type: application/json" \
  -d '{"title":"Updated"}'

# Delete — expect 204 and an empty body
curl -i -X DELETE http://localhost:3000/notes/1

# Delete it again — expect 404
curl -i -X DELETE http://localhost:3000/notes/1
💡

The -i flag prints the response headers, including the status line. Without it you only see the body and you cannot tell 200 from 201 from 404. Use -i while testing.

Verify — your API is correct if all of these pass
  • GET /notes/9999 returns 404, not an empty 200.
  • POST /notes with no title returns 400.
  • POST /notes with a title returns 201 and includes the new id.
  • DELETE on an existing note returns 204 with an empty body.
  • The same DELETE run twice returns 204 then 404 — and the data is identical either way.

Assignment — Rebuild It in Hono
A framework I am not going to teach you
Why This Assignment Exists

If you can build the same API in a framework nobody taught you, then you learned backend. If you cannot, you learned Express syntax. The concepts are the thing that transfers between jobs; the syntax is looked up in thirty seconds.

Hono is a small, fast web framework. Its routing looks familiar on purpose, but request and response handling are different — you will have to read the documentation, and that is the point. Reading docs is the skill.

Getting started 
npm create hono@latest notes-hono
# choose the nodejs template if you do not have Bun installed
Base
  • Finish the Express version properly — all five routes, correct status codes, 404 and 400 handled.
  • Test every route with curl and save the commands in a requests.http or a text file.
Push
  • Rebuild all five routes in Hono. Same paths, same methods, same status codes.
  • Write three lines in your README on what was different and what was identical.
  • Add GET /notes?search= to both versions and keep the behaviour the same.
Break
  • Add a second resource — /notes/:id/tags — and design the routes yourself using the naming rules in section 3.
  • Prove your PUT is idempotent: run it five times and show the state is unchanged after the first.
  • Add pagination with ?page= and ?limit=, and return the total count in a header.
💡

Hono runs on Bun, which is the same runtime we will use later in the industry simulation. Tonight's homework is quietly setting up something you will need in a few weeks.

One-Line Summary

An API is a contract. REST is a shared convention for writing that contract: URLs are nouns, methods are verbs, status codes tell the truth, and the server remembers nothing between requests.
